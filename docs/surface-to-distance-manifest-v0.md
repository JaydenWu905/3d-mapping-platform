# Surface → Distance Manifest — Draft / v0

Status: discussion draft. Nothing in this document is a formal compatibility guarantee yet.

This draft records what the current real MrHash-LiDAR Surface run produces and what the Distance
module must decide before a versioned hand-off can be implemented. The current Surface
`result_manifest.json` uses schema `0.1`; there is no real Distance runner or dedicated
Surface-to-Distance input manifest yet.

## Current Surface outputs

| `artifact_id` | Role | Current content type | Confirmed content | Intended use |
|---|---|---|---|---|
| `surface_mesh` | `data` | `application/octet-stream` | Complete native MrHash mesh PLY | Candidate Distance input |
| `voxel_points` | `data` | `application/octet-stream` | Native voxel-point PLY | Candidate Distance input |
| `hash_points` | `data` | `application/octet-stream` | Native hash-point PLY | Diagnostics or future input, semantics not yet contracted |
| `surface_model` | `preview` | `model/gltf-binary` | Simplified GLB built from `surface_mesh` | Browser preview only; never the authoritative Distance input |
| `run_config` | `data` | `text/plain` | Per-run MrHash configuration | Provenance |

The complete PLY and simplified GLB are deliberately different artifacts. `surface_mesh` is the
complete algorithm output. `surface_model` is generated by exact-vertex welding and optional
quadric edge-collapse for interactive viewing; it may have fewer vertices/faces and must not be
substituted for the full mesh without an explicit third-module decision.

## Strictly confirmed PLY layouts

The adapter reads and validates PLY headers. A real smoke output confirmed these layouts:

- `surface_mesh`: ASCII PLY; vertex properties `x y z red green blue`; face property
  `vertex_indices`.
- `voxel_points`: binary little-endian PLY; vertex properties
  `x y z sdf weight red green blue alpha`.
- `hash_points`: binary little-endian PLY; vertex properties
  `x y z weight red green blue alpha`.

The code currently enforces only that `voxel_points` contains `x y z sdf weight rgba`; it checks
that each PLY has a format and non-zero vertex count and records mesh faces/counts. Property names
above are observations from the accepted output, not yet a versioned schema guarantee.

The Surface result currently confirms `frame_id: "world"`, `unit: "meter"`, backend
`mrhash_lidar`, a per-run `run_id`, mode, entrypoint, source topic, Pose semantics, and a
`run_config` artifact. It records mesh/voxel/preview sizes, but not every artifact size. It records
preview bounds and source-mesh bounds computed during preview generation. It records SHA-256 only
for the GLB preview, not yet for every full PLY. Therefore the future contract below requires
fields that the current result manifest still needs to add before implementation.

## Unknown semantics — do not infer

The following are not established by the platform adapter or current manifest:

- whether positive or negative `sdf` means free space or interior;
- SDF truncation distance, clamping, normalization, or storage precision guarantees;
- physical voxel size and whether points denote centres, corners, or samples;
- meaning, range, accumulation rule, or valid threshold for `weight`;
- how unknown/unobserved space is represented;
- whether RGBA is geometry color, diagnostic coloring, or algorithm state;
- meaning and spatial role of `hash_points` and its weight;
- whether voxel samples form a complete regular grid or only allocated/observed entries;
- mesh watertightness, manifoldness, winding, normal orientation, or duplicate policy.

These items remain **TBD** and must not be treated as guarantees based only on field names.

## Proposed v0 hand-off

The Distance input preparer should resolve artifacts by ID and role from a completed Surface
result, apply the same relative-path containment, symlink resolution, existence, byte-size, and
SHA-256 rules as the Pose → Surface boundary, and atomically write a dedicated input manifest.
All authoritative artifacts should carry `frame_id`, coordinate unit, axis-aligned bounds,
`size_bytes`, and `sha256`. Provenance should include Surface backend, run ID, algorithm version or
revision, and configuration artifact/source.

The third module must choose one primary representation:

1. **Voxel field.** Agree on voxel size, sample location, SDF sign and truncation, valid weight
   threshold, unknown-region representation, sparse indexing, and whether resampling belongs to
   Surface or Distance.
2. **Mesh.** Agree on topology requirements, coordinate frame and units, winding/normals,
   watertight/manifold expectations, degenerate/duplicate cleanup, and which module owns
   voxelization or other preprocessing.

`surface_model` must remain preview-only in either option.

## Questions for the third module

1. Is the preferred authoritative input `voxel_points`, `surface_mesh`, or both with one as a
   fallback?
2. If voxel-based: what are voxel size, sample location, SDF sign/truncation, valid weight
   threshold, unknown representation, and sparse-grid indexing requirements?
3. If mesh-based: are watertightness, manifoldness, winding, normals, or cleanup mandatory, and
   which module owns preprocessing/voxelization?
4. Must `hash_points` be consumed, retained only for diagnostics, or excluded from the contract?
5. Which coordinate-frame/right-handedness guarantees and bounding-box convention are required?
6. Which PLY formats/property types are accepted, and should content types become a specific PLY
   media type rather than `application/octet-stream`?
7. What maximum file sizes, streaming behavior, and memory limits must the preparer enforce?
8. Which algorithm/version/configuration fields are mandatory for reproducibility?
9. What validation failures are blocking, and which geometry-quality conditions are warnings?
